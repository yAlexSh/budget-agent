# Агент семейного бюджета

Учебный прототип: Telegram/CLI-агент на архитектуре SGR + RAG + внешний MCP.
Полное описание дизайна — `docs/2026-08-23-design.md`. Этот файл — только
инструкция по разворачиванию и проверке.

Этот файл — про установку. Как пользоваться готовым ботом, описано
отдельно в `КАК_ПОЛЬЗОВАТЬСЯ.md`.

## Требования

- Python 3.11+
- Docker (для Postgres 18 + pgvector) — либо уже поднятый Postgres 18 с
  расширением `pgvector` по любому другому пути
- Локальная или облачная Ollama, доступная по `OLLAMA_URL`/`EMBED_URL`, с
  моделями `gpt-oss:120b-cloud` (или другой из лестницы ниже) и
  `qwen3-embedding:0.6b`
- `uv`/`uvx` в `PATH` — им запускается MCP-сервер курсов ЦБ
  (`uvx atomno-mcp-cbr-rates@0.1.10`)
- Токен Telegram-бота — только если нужен Telegram-слой, для CLI-проверки
  не требуется

## Быстрый путь

```bash
./setup.sh
```

Механически выполняет шаги 2, 3 и 4 ниже: создаёт `.venv` (если его ещё нет),
ставит зависимости, копирует `.env.example` в `.env` (если `.env` ещё нет),
спрашивает два значения, которые нельзя угадать автоматически — строку
подключения к Postgres (`PG_DSN`) и токен Telegram-бота — и в конце сам
запускает предполётную проверку `--doctor` и печатает, что делать дальше.
Безопасен при повторном запуске: не пересоздаёт `.venv` и не затирает
существующий `.env`. Postgres (шаг 1) `setup.sh` не поднимает — это
отдельная команда `docker compose up -d`, до или после скрипта, не важно.
Раз `--doctor` уже отработал внутри скрипта, после него можно сразу
переходить к шагу 5 — индексации.

## 1. Поднять Postgres

```bash
docker compose up -d
```

Поднимает `pgvector/pgvector:0.8.6-pg18-trixie` на `127.0.0.1:5433`, база
`budget`, пользователь/пароль `budget`/`budget` (см. `docker-compose.yml`).
Если используете свой Postgres — создайте пустую базу и включите в ней
`CREATE EXTENSION vector` вручную либо доверьте это `--init` (шаг 5 делает
это сам).

**Важно: схема создаётся только на пустой базе.** Все таблицы создаются
через `CREATE TABLE IF NOT EXISTS` — существующие таблицы не мигрируются и
не проверяются на соответствие текущей схеме. Если запустить `--init` на
базе, оставшейся от предыдущей версии кода (другой набор колонок), несовпадение
проявится не сразу и не с понятной ошибкой, а как SQL-сбой в случайном месте
при первом запросе к «неправильной» таблице. Всегда начинайте с пустой базы
(`docker compose down -v && docker compose up -d`, если поднимали контейнером
раньше).

**После обновления с версии без `dialog_state.user_id` базу нужно пересоздать.**
В текущей схеме состояние диалога разделено по `(chat_id, user_id)`, а для
`transactions.amount` добавлено ограничение положительной суммы. Проект не
выполняет миграции существующей схемы, поэтому старый volume нужно удалить
командой `docker compose down -v`, снова поднять Postgres и повторить `--init`
(индексация займёт около восьми минут). `--doctor` определяет старую схему и
сообщает об этом до запуска бота.

## 2. Установить зависимости

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

> **Замечание про `pip`:** на Debian/Ubuntu без пакета `python3-venv` виртуальное
> окружение создаётся без `pip` — `.venv/bin/pip` не существует, и строка
> `.venv/bin/pip install -r requirements.txt` падает с «No such file or directory».
> Установите `python3-venv` (`sudo apt install python3-venv`) или используйте `uv`:
> `uv venv --python 3.11 .venv && uv pip install --python .venv/bin/python -r requirements.txt`

## 3. Заполнить `.env`

```bash
cp .env.example .env
```

Откройте `.env` и задайте как минимум:

- `PG_DSN` — строка подключения к базе из шага 1, например
  `postgresql://budget:budget@127.0.0.1:5433/budget`
- `OLLAMA_URL`, `OLLAMA_MODEL` — адрес Ollama и модель для демо
  (`gpt-oss:120b-cloud`) или своя модель из лестницы ниже
- `EMBED_URL`, `EMBED_MODEL` — обычно тот же адрес Ollama,
  `qwen3-embedding:0.6b`
- `TELEGRAM_BOT_TOKEN` — только для Telegram-слоя, см. следующий пункт
- `PERSON_HUSBAND_TG_ID`, `PERSON_WIFE_TG_ID` — числовые Telegram id мужа и
  жены (бот резолвит роль по этому id, а не по имени)
- `TELEGRAM_ALLOWED_GROUP_CHAT_IDS` — разрешённые групповые `chat_id` через
  запятую. Пустое значение запрещает работу бота во всех группах.

Остальные переменные (`ROUTER_*`, `MCP_*`, `LLM_STRUCTURED_MODE`,
`BROADCAST_STEPS`, ...) можно оставить как в `.env.example` — это запасной
путь и тонкая настройка, для базового прогона не нужны.

> **Внимание, inline-комментарии в `.env`:** не пишите `KEY=   # комментарий` в одной
> строке для ключей, значение которых должно быть пустым (например
> `TELEGRAM_ALLOWED_GROUP_CHAT_IDS`, `TELEGRAM_REPORT_CHAT_ID`). `python-dotenv` срезает
> комментарий только если перед `#` есть непустое значение; при пустом значении комментарий
> сам становится значением, и `--init`/`--telegram`/CLI падают с
> `ValueError: invalid literal for int()` (или получают мусорную строку). Комментарий для
> пустых ключей держите на отдельной `#`-строке — как в исправленном `.env.example`.

### Получение токена у @BotFather

1. В Telegram откройте чат с `@BotFather`.
2. Отправьте `/newbot`, задайте имя и username бота (username должен
   заканчиваться на `bot`).
3. BotFather пришлёт токен вида `123456789:AAxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx` —
   вставьте его в `TELEGRAM_BOT_TOKEN`.
4. Чтобы узнать свой Telegram id для `PERSON_HUSBAND_TG_ID`/`PERSON_WIFE_TG_ID`,
   напишите что угодно боту `@userinfobot` — он ответит числовым id.

Чтобы получить `chat_id` группы для `TELEGRAM_ALLOWED_GROUP_CHAT_IDS`, добавьте
бота в группу, временно остановите polling, отправьте в группу сообщение и
откройте `https://api.telegram.org/bot<TOKEN>/getUpdates`: нужное значение
находится в `result[].message.chat.id`. Идентификатор группы отрицательный,
у супергруппы обычно начинается с `-100`. После записи значения в `.env`
снова запустите бота.

## 4. Проверить окружение (`--doctor`)

```bash
.venv/bin/python budget_agent.py --doctor
```

**Перед индексацией стоит запустить эту команду.** `--init` занимает около
восьми минут (следующий раздел), и, если что-то настроено неверно —
`.env` не заполнен, Postgres не отвечает, эмбеддинг-модель не загружена,
база уже не пустая, языковая модель не отвечает, — без `--doctor` об этом
узнаёшь только после этих восьми минут. Сама проверка укладывается в
секунды: печатает по строке на каждую из десяти проверок с отметкой `OK`
(всё хорошо), `ПРОБЛЕМА` (мешает работе, есть точное указание что делать)
или `ВНИМАНИЕ` (не мешает, но стоит знать — например, не задан токен
Telegram). Код возврата ненулевой, если есть хоть одна `ПРОБЛЕМА`.

Проверка языковой модели делает один пробный запрос — если это сейчас
нежелательно (квота, оффлайн-разработка), пропустите её флагом:

```bash
.venv/bin/python budget_agent.py --doctor --no-llm
```

`--doctor` работает и без `.env` вовсе — сообщает, каких переменных не
хватает, вместо того чтобы просто упасть.

## 5. Индексация (`--init`)

```bash
.venv/bin/python budget_agent.py --init
```

Создаёт схему и последовательно загружает: оба корпуса RAG (`knowledge.md` —
50 статей `PF-001…PF-050`, `household.md` — 12 заметок `HH-001…HH-012`) и
сид-данные (`seed_data.json`).

**Первичная индексация занимает около восьми минут.** Эмбеддинги считаются
по одному документу — 62 документа, на каждый уходит несколько секунд
обращения к `qwen3-embedding:0.6b`. Команда печатает прогресс по каждому
документу (`[N/50] knowledge: PF-00N — Название`), поэтому восемь минут
тишины быть не должно — если вывод не появляется вовсе, это уже реальная
проблема (недоступна Ollama по `EMBED_URL`), а не нормальная работа
команды. Не прерывайте её раньше времени, ориентируясь на «зависла»: пока
номера документов растут, всё в порядке.

Ожидаемый вывод в конце:
```
документов: 62
сид: {'persons': 2, 'categories': ..., 'accounts': 6, ...}
```

Повторный `--init` на уже заполненной базе безопасен для документов и схемы
(`ON CONFLICT ... DO UPDATE`, `CREATE TABLE IF NOT EXISTS`). Сид он не
перезаливает: печатает «сид: пропущен — …» и продолжает как обычно — в
таблицах транзакций/счетов/целей к этому моменту могут быть уже настоящие
траты, введённые через бота, а не только сид (см. докстринг `SeedNotEmpty` в
`budget_agent.py`), и без явного согласия перезаписывать их нельзя.

Если действительно нужно стереть текущие транзакции/счета/цели и перезалить
`seed_data.json` поверх них (например, после перегенерации сида под свежую
дату — см. следующий раздел), добавьте флаг `--reset`:

```bash
.venv/bin/python budget_agent.py --init --reset
```

## 6. Проверить бэкенд

```bash
.venv/bin/python budget_agent.py --check-backend
```

Печатает провайдера, модель и то, какой из трёх режимов структурированного
вывода (`strict` / `json_object` / `prompt`) реально поддерживает
подключённая модель — от этого зависит, насколько строго можно требовать от
неё соответствие схеме.

## 7. Проверка через CLI

```bash
.venv/bin/python budget_agent.py "Сколько мы потратили на продукты в июле?"
.venv/bin/python budget_agent.py --as wife --chat group "Хватит ли нам денег до зарплаты?"
```

Без флагов `--as`/`--chat` вопрос идёт от лица мужа в личном чате. Полный
прогон всех 12 демо-сценариев с замером времени — `run_demo.py` (см.
`demo_scenarios.md`):

```bash
.venv/bin/python run_demo.py
```

## 8. Запуск Telegram

```bash
.venv/bin/python budget_agent.py --telegram
```

Поллинг, без вебхука. Команды `/start`, `/status`, `/report`, `/help`,
свободный текст и кнопка «Совет от ИИ» под `/report`. Остановка — `Ctrl+C`.

## 9. Cron для ежедневного отчёта

Отчёт по вчерашним тратам в общий чат — отдельная точка входа, без своего
демона:

```cron
0 9 * * * cd /путь/до/budget-agent && .venv/bin/python budget_agent.py --report-cron >> report.log 2>&1
```

Без `TELEGRAM_BOT_TOKEN` отчёт печатается в stdout — так можно проверить
команду до настройки бота. С токеном нужен ещё `TELEGRAM_REPORT_CHAT_ID`
(id общего чата) в окружении — без него отчёт тоже уйдёт в stdout с
объяснением, а не потеряется молча.

| `household.md` | корпус RAG `doc_type=household`: семейные правила и заметки о крупных тратах |
| `.env.example` | шаблон конфигурации |
| `setup.sh` | первичная настройка: `.venv`, зависимости, `.env`, предполётная `--doctor` |
| `requirements.txt` | зависимости |
| `docker-compose.yml` | Postgres 18 + pgvector |
| `КАК_ПОЛЬЗОВАТЬСЯ.md` | инструкция для того, кто будет с ботом разговаривать |
| `README.md` | эта инструкция |
| `demo_scenarios.md` | протокол прогона 12 демо-сценариев |
| `run_demo.py` | скрипт, который этот прогон производит |
| `docs/2026-08-23-design.md` | дизайн-документ, полное описание проекта |

`seed_data.json` привязан к дате своей генерации: последние восемь полных
календарных месяцев плюс неполный текущий месяц (от 1-го числа по день
генерации) — только так `/status` и `/report` показывают данные за текущий
месяц сразу после `--init`, а не «Потрачено 0 ₽». Если проверка идёт заметно
позже даты в этом файле (текущий месяц уже другой), перегенерируйте сид
одной командой:

```bash
.venv/bin/python make_seed.py
```

На чистой базе достаточно затем обычного `--init` (раздел 5) — данных ещё
нет, `SeedNotEmpty` не сработает, `--reset` не нужен.

Если документы (RAG-корпуса) уже проиндексированы и повторная индексация не
нужна, `--init` всё равно заново её выполнит — `ON CONFLICT ... DO UPDATE`
не экономит время, эмбеддинг считается заново для каждого документа, это
опять те же восемь минут (раздел 5). Чтобы освежить только транзакции, минуя
`--init` целиком, перезалейте сид напрямую коротким скриптом:

```bash
.venv/bin/python -c "
from budget_agent import db, load_seed
with db() as conn:
    print(load_seed(conn, force=True))
"
```

`make_seed.py` детерминирован фиксированным `random.seed`, но зависит от
текущей календарной даты запуска (`ANCHOR_DATE = date.today()`) — два
запуска в разные дни дают разные файлы, это ожидаемо.

`test_budget_agent.py` в состав поставки в этой таблице не входит и не
лежит рядом с `budget_agent.py` — он прилагается отдельным файлом к этой
инструкции (в той же облачной папке). `pytest` в `requirements.txt` нужен
именно для него — самому агенту он не требуется.

**Тесты не запускать параллельно с другой работой на той же базе.**
`test_budget_agent.py` перед прогоном грузит сид принудительной
перезаписью (`load_seed(conn, force=True)`), а часть тестов читает
агрегаты по всей таблице транзакций — параллельный прогон (или прогон
одновременно с ручной проверкой через CLI/Telegram на той же базе) даёт
гонку: одна сессия чистит и перезаливает таблицы, пока другая их читает
или пишет, и это всплывает как нарушение внешних ключей или неверные суммы,
а не как явная ошибка блокировки. Прогоняйте `pytest` последовательно и на
базе, которую в этот момент больше никто не трогает — для экспериментов
отдельно от `budget` держите отдельную базу (например, `budget_test`).

> **Подготовка тестовой базы перед первым `pytest`:** тесты наполняют базу только сидом
> (`load_seed`), а RAG-корпуса (`knowledge.md`, `household.md`) попадают в таблицу
> `documents` только через `--init`/`load_documents`. На пустой тестовой базе
> `test_search_knowledge_returns_only_pf` и `test_search_household_returns_only_hh`
> падают с `assert ([])` — это не баг, а отсутствие документов. Перед прогоном выполните
> на тестовой базе `--init` и направьте тесты на неё через `PG_DSN`:
> `PG_DSN=<тестовая-база> .venv/bin/python budget_agent.py --init && PG_DSN=<тестовая-база> .venv/bin/python -m pytest test_budget_agent.py`.

## Лестница моделей закрытого контура

Из раздела 11 `docs/2026-08-23-design.md`. `OLLAMA_MODEL` — параметр
конфигурации, интерфейс к модели единый, но выбор не безразличен:
от модели зависят формат ответа, качество выбора инструмента, задержка и
частота повторов. Модель подбирается под железо заказчика:

| Модель | Вес | Требуется на месте |
|---|---|---|
| `gpt-oss:20b` | ~13 ГБ MXFP4 | станция 16 ГБ, идёт даже на CPU |
| `gemma4:31b` | ~20 ГБ Q4 | станция 32 ГБ |
| `gpt-oss:120b` | ~60 ГБ MXFP4 | H100 80 ГБ, Mac Studio 128 ГБ или сервер 96+ ГБ |
| `nemotron-3-super` | ~60 ГБ NVFP4 | то же по памяти; MoE — активных параметров меньше, инференс быстрее плотной модели того же размера, NVFP4 раскрывается на Blackwell |

Остальные компоненты одинаковы на любой ступени: эмбеддинги
`qwen3-embedding:0.6b` — 0,6 ГБ диска и ~0,7 ГБ памяти, Postgres с pgvector —
около 0,3 ГБ, процесс агента — 0,2 ГБ.

Каждая ступень должна пройти одинаковый набор smoke-сценариев (см.
`demo_scenarios.md`) с замером p95 задержки — «модель запускается на этом
железе» само по себе не значит, что она пригодна для Telegram-бота.

Различие, которое обязан знать код: `gpt-oss` и `nemotron` возвращают
рассуждения отдельным полем и могут отдать пустой `content`; `gemma4`
отдельного поля не имеет и пустого `content` не даёт, но оборачивает JSON в
markdown — слой LLM (`budget_agent.py`, раздел 2) обрабатывает оба
поведения.

Демо и сдача используют `gpt-oss:120b-cloud` (облачная Ollama,
конфигурация не меняется под размер модели) — для самого прогона
демо-сценариев ступень из таблицы выше значения не имеет, она нужна только
при развёртывании в закрытом контуре на своём железе.
