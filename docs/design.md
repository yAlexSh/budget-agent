# Дизайн: агент семейного бюджета

Статус: реализовано. Документ живой — правится вслед за кодом, историю правок держит git.

## 1. Карточка задания

**Роль пользователя.** Частное лицо, ведущее совместный бюджет с супругой. Не финансист и не аналитик: нужен ответ на вопрос, а не отчётность.

**Выбранная задача.** Отвечать на вопросы о состоянии семейного бюджета, прогнозировать кассовые разрывы, помогать планировать крупные траты и отпуск, а также консультировать по принципам управления личными финансами с указанием источников.

**Пользователи будущего помощника.** Двое взрослых членов семьи. Общий чат — для совместных вопросов, личные чаты — для персональных.

**Ожидаемый результат работы агента.** Структурированный ответ в Telegram: краткий практический вывод; цифры с указанием, откуда они взяты; несколько сценариев, если однозначного ответа нет; источники для образовательных вопросов; оговорка о границе применимости. Для ввода траты — подтверждение с распознанной категорией.

**Границы его компетенции.** Не даёт персональных инвестиционных рекомендаций — объясняет подходы и последствия вариантов. Не совершает платежей и переводов, только учёт. Актуальные ставки, курсы и инфляцию берёт из внешнего MCP Банка России и всегда указывает дату; курс ЦБ не равен курсу обмена в банке, и агент это оговаривает. Не показывает личные данные одного супруга другому. Работает только с внесёнными данными — к банкам не подключается.

**Примечание.** Учебный прототип. История трат — сгенерированная сид-база за девять месяцев плюс ручной ввод через бота. Корпус знаний — собственные конспекты со ссылками на первоисточники; тексты книг не загружаются.

Ниже тот же путь текстом, с внутренним порядком шагов цикла, которого на картинке не видно:

```
Telegram / CLI
      │
      ▼
 определение пользователя  →  контекст видимости (person, chat_type)
      │
      ▼
 SGR-цикл ────────────────────────────────────┐
      │  NextStep: прогресс → план → рассуждение → инструмент
      │                                        │
      ├─► инструменты бюджета (Postgres)       │
      ├─► RAG-поиск (pgvector)                 │
      ├─► MCP Банка России (stdio, uvx)        │
      │                                        │
      └─► task_completed ──► FinalAnswer ──────┘
                                  │
                                  ▼
                    структурированный ответ пользователю
```

Ключевое: контекст видимости вычисляется один раз на входе и передаётся в каждый инструмент. Инструмент физически не возвращает того, что не положено видеть, — приватность обеспечивается фильтром в запросе, а не просьбой к модели.

## 4. Структура единственного файла

Поставляется один `budget_agent.py`. Разделы:

1. Конфигурация — переменные окружения, ничего захардкоженного
2. Слой LLM — клиент, `structured_call`, отключение thinking
3. Эмбеддинги — Ollama `/api/embed`
4. Хранилище — подключение, схема, загрузка сид-данных
5. Инструменты бюджета — функции + схемы аргументов
6. RAG — индексация корпусов и раздельный поиск
7. MCP-клиент — stdio JSON-RPC (наследие `a06`)
8. SGR-цикл — `NextStep`, исполнение, финализация
9. Быстрый путь — команды, состояния диалога, отчёты по расписанию
10. Telegram — поллинг, страж очереди простоя, `callback_query`, очередь трансляции шагов
11. CLI — режим проверки без Telegram

Ориентир на старте — 1100–1200 строк; по факту вышло около 2000 (финальная
волна правок, пункт 10) — выросло по ходу разработки за счёт докстрингов,
объясняющих неочевидные решения по каждому раунду ревью, и защитных веток,
которых не было в первом черновике. Данных в файле нет.

## 5. Слой структурированного вывода

Мозги сменные, возможности бэкендов разные — проверено экспериментально 2026-08-23:

| Бэкенд | Строгая схема | Источник |
|---|---|---|
| Ollama **локально** (любая модель) | соблюдается — constrained decoding | измерено: `tinyllama` вернула ровно поля схемы |
| Ollama **`:cloud`** | параметр принимается и **молча игнорируется** | измерено на трёх моделях: `gpt-oss:120b`, `gpt-oss:20b`, `gemma4:31b` — каждая вернула собственную форму (`{action, action_input}`, `{tool, parameters}`) |
| `deepseek-v4-flash` | нет, только `json_object` | документация DeepSeek |
| Роутер курса (`gpt-4o-mini`) | да, `json_schema` + `strict` | документация |

**Отказ облачной Ollama — молчаливый.** Запрос принят, JSON валиден, поля чужие. Это опаснее явной ошибки, поэтому автоопределение режима строится не на «приняло ли API параметр», а на **сверке фактических полей ответа со схемой**. Команда `--check-backend` отправляет пробный запрос с известной схемой и сравнивает набор ключей; режим `strict` назначается только при точном совпадении.

**Рассуждения в отдельном поле.** `gpt-oss` возвращает их в `reasoning` (OpenAI-совместимый ответ) или `thinking` (нативный `/api/chat`), а `content` при этом бывает пустым. DeepSeek документирует тот же эффект при JSON Output. Слой LLM обязан считать пустой `content` ошибкой шага и уходить в повтор, а не принимать его за ответ.

**Бесплатный доступ Ollama cloud** покрывает `gpt-oss:120b/20b` и `gemma4:31b`; `qwen3.5:cloud` и `deepseek-v4-flash:cloud` отвечают 403 и требуют платной подписки — то есть добраться до DeepSeek через Ollama нельзя, нужен отдельный ключ.

**Одна и та же модель даёт разный уровень в зависимости от того, где исполняется.** `gpt-oss:20b` локально — первый уровень (сэмплер принуждает схему), `gpt-oss:20b-cloud` — третий (параметр отбрасывается). Отсюда рабочий порядок: **разработка ведётся на облачном варианте, то есть на худшем уровне, а поставка идёт в закрытый контур на локальном, то есть на лучшем.** Если агент устойчив там, где схему не гарантирует ничто кроме разбора и повтора, в целевой среде он заработает тем более. Обратный порядок был бы ловушкой — отладка на строгом режиме и сюрпризы у заказчика.

Функция `structured_call(schema, messages)` работает в трёх режимах, выбираемых `LLM_STRUCTURED_MODE` (по умолчанию — автоопределение):

- `strict` — `response_format: json_schema`, `strict: true`, `additionalProperties: false`
- `json_object` — `response_format: json_object`, схема и пример JSON вкладываются в промпт (DeepSeek требует слова «json» в тексте)
- `prompt` — схема текстом, устойчивый разбор ответа: снятие markdown-обёртки ` ```json ` и выделение внешнего объекта. Типы **не приводятся** — см. запрет ниже

Поверх любого режима — валидация Pydantic и **один повтор** с текстом ошибки, подмешанным в промпт. Повтор обязателен: и пустой `content`, и JSON с чужими полями обрабатываются наравне с несовпадением типов.

Режим размышления DeepSeek выключается принудительно: `extra_body={"thinking": {"type": "disabled"}}`. Причины — при включённом thinking не действуют `temperature` и `top_p`, а при наличии `tools` требуется таскать `reasoning_content` в контексте под угрозой 400-й ошибки. Плюс концептуальная: SGR-схема сама задаёт каркас рассуждения, встроенный chain-of-thought поверх неё избыточен.

Отдельная команда `--check-backend` прогоняет три пробных вызова и печатает, какой режим держит текущий бэкенд. Нужна при переезде на локальную Ollama и при первичной настройке на новой машине.

## 6. Модель данных

Postgres 18 + pgvector. Валюты — RUB (основная) и USD.

```
persons(id, name, role, telegram_id)                       -- husband | wife
accounts(id, name, kind, currency, opening_balance, scope) -- cash | card | deposit
categories(id, name, kind)                                 -- expense | income
transactions(id, ts, amount, currency, account_id,
             category_id, merchant, comment, scope, person_id)
recurring(id, title, amount, currency, day_of_month,
          category_id, scope, active, note)
goals(id, title, target_amount, currency, due_date,
      saved_amount, scope)
merchant_aliases(alias, category_id, scope)                -- обучаемая категоризация
budget_limits(person_id, period, amount, currency, scope)  -- месячный лимит трат
dialog_state(chat_id, user_id, person_id, state, pending jsonb,
             updated_at)  PRIMARY KEY (chat_id, user_id)    -- состояние диалога
family_rules(key, value_num, value_text, currency,
             unit, document_key, scope)                    -- типизированные пороги
documents(id, document_key UNIQUE, doc_type, title, source,
          scope, text, keywords text[], metadata jsonb,
          embedding VECTOR(1024))
```

`scope ∈ {common, husband, wife}` — в `accounts`, `transactions`, `recurring`, `goals`, `documents`, `family_rules`.

`budget_limits.person_id` объявлена в схеме, но нигде не используется:
`get_budget_status` и `add_expense` фильтруют лимит по `scope`, как и
остальные таблицы, а не по конкретному человеку — «месячный лимит трат» на
деле привязан к области видимости (`common`/`husband`/`wife`), а не к
персоне отдельно от неё. Колонка — задел на случай, если персональные
лимиты внутри одной области видимости понадобятся позже (финальная волна
правок, пункт 10).

`doc_type ∈ {knowledge, household}` — конспекты по финансам и семейные заметки. Retrieval фильтрует по типу и по видимости.

**Баланс вычисляется, а не хранится.** `opening_balance` плюс сумма транзакций по счёту — один источник истины. Хранимое поле `balance` рядом с журналом транзакций создавало бы второй, который рано или поздно разойдётся.

**Управляющие числа живут в `family_rules`, а не в прозе.** Порог обсуждения крупной покупки (45 000), цель резерва (550 000), доля личных денег — типизированные значения со ссылкой `document_key` на заметку, которая их объясняет. Принцип тот же, что «не давать модели считать»: RAG объясняет правило, код применяет число. Вытаскивать порог из текста заметки семантическим поиском ненадёжно.

Версионирования документов (`valid_from`, `supersedes`, `reviewed_at`) в прототипе нет осознанно: 62 статических документа приезжают вместе с кодом и внутри прототипа не обновляются.

Оба корпуса готовы и структурно совместимы: 50 статей `PF-001…PF-050` и 12 заметок `HH-001…HH-012`. Структура одинакова — заголовок, `**Ключевые слова:**`, тело, пара «вопрос — ответ»; у `HH` добавлено обязательное поле `**Область:**`.

Парсер общий по каркасу (`## (PF|HH)-\d+`), но с **двумя профильными валидаторами**: для `PF` поле области отсутствует и `scope` проставляется `common`, для `HH` область обязательна и должна быть одним из трёх допустимых значений. Одного регулярного выражения недостаточно — валидатор ловит заметку без области или с опечаткой в ней до загрузки в базу. `document_key` (`PF-007`, `HH-002`) идёт в одноимённую колонку, ключевые слова — в `keywords`. Прочие поля вида `**Ключ:**` складываются в `metadata jsonb` как есть — так корпус расширяется без правки схемы (например, `**Тип:**` в `HH-005`, помечающий заметку как стратегию семьи, а не образовательный принцип).

Индекс по векторам не строится: на шестидесяти с небольшим документах последовательный перебор быстрее.

## 7. Инструменты

Обычные Python-функции в том же файле; собственный MCP-сервер не нужен, критерий «использует инструмент» закрывают они.

```
get_balance()                          остатки по счетам, раздельно RUB и USD
get_expenses(period, category?)        суммы по категориям за период
get_recurring()                        регулярные платежи
get_goals()                            цели накопления, включая отпуск
get_family_rule(key)                   типизированное значение правила семьи
get_budget_status()                    лимит месяца, потрачено, остаток, процент
get_income(period)                     доходы за период по категориям, итог рублёвый
forecast_cashflow(months)              помесячный прогноз, поиск кассового разрыва
set_budget_limit(amount)               подготовить смену месячного лимита
search_knowledge(query)                RAG только по PF: общие принципы
search_household(query)                RAG только по HH: договорённости семьи
cbr_get_rate(char_code)                курс ЦБ на сегодня: USD | EUR | CNY
cbr_key_rate()                         ключевая ставка ЦБ
cbr_inflation(year_from?, year_to?)    инфляция по данным ЦБ
```

Четырнадцать функций реестра `TOOL_REGISTRY` — ровно то, что агент может вызвать
из SGR-цикла. Три последних ходят во внешний MCP-сервер ЦБ (раздел 9), остальные
работают с базой и корпусами. `set_budget_limit` лимит не пишет: он готовит
смену, а записывает её подтверждение (раздел «Состояние диалога»). Каждая
функция реестра обязана иметь класс вызова в размеченном объединении
`ToolCall` — иначе она есть в реестре, но модель не может её назвать.

`add_expense` и `categorize` в реестр не входят и агенту не видны — это функции
пути обработки траты (раздел 9а): свободный текст разбирается детерминированно,
без SGR-цикла.

Каждая получает контекст видимости неявно и подмешивает `WHERE scope IN (...)`.

Инструменты периода считают в рублях: конвертация — отдельный вопрос (курс на какую дату, по ЦБ или банковский), и подмешивать её в итог нельзя. Операции в других валютах возвращаются отдельным полем `other_currencies`, а `/status` и `/report` дописывают о них строку — молчаливое исключение из итога однажды уже дало уверенно неполный ответ про заработок (ревью PR #20).

### Маршрутизация retrieval — детерминированная

Два раздельных инструмента вместо одного с необязательным `doc_type`. Общий top-k по обоим корпусам недопустим: на запрос про подушку одновременно претендуют `PF-006`, `PF-007` и `HH-002`, хотя роли у них разные.

| Тип вопроса | Источник |
|---|---|
| Общий образовательный («зачем нужен резерв») | только `search_knowledge` |
| «Как у нас принято» | только `search_household` |
| «Сколько у нас» | только SQL-инструменты |
| Персонализированный совет | отдельный top-k из каждого корпуса плюс SQL, затем синтез |

Разделение по ролям: SQL — факты текущего состояния, `HH` — договорённости и история семьи, `PF` — общие принципы. Семейное правило не опровергает общий принцип, а конкретизирует его. В синтез уходит не больше одного-двух результатов из каждого корпуса.

Раздельные имена инструментов лежат в `Literal` схемы `NextStep`, поэтому модель обязана выбрать корпус явным шагом — это надёжнее необязательного параметра, который она может не заполнить.

**Категоризация — каскад:** точное совпадение в `merchant_aliases` (ноль токенов) → классификация LLM по списку категорий → при низкой уверенности агент переспрашивает в чате, а ответ дописывается в `merchant_aliases`. Со временем дорогой путь используется всё реже.

### Состояние диалога

Каскад категоризации обрывает обработку на середине: трата разобрана, категория неясна, задан вопрос — и следующее сообщение пользователя нужно понять как ответ именно на него. Без состояния эта ветка не работает.

`dialog_state` хранит состояние и `pending jsonb` с незавершённым действием по паре `(chat_id, user_id)`, а не по одному чату: в общем чате муж и жена ведут разные незавершённые диалоги, и ответ одного не должен закрывать вопрос, заданный другому.

```
base            — обычная работа, сообщение идёт агенту
awaiting_limit  — задан вопрос о месячном лимите (после /start)
awaiting_category — задан вопрос о категории; в pending лежит разобранная трата
awaiting_limit_confirm — агент подготовил смену лимита; в pending лежат новая и прежняя суммы
awaiting_income_category — задан вопрос о категории дохода; в pending лежат сумма, источник и валюта
```

`awaiting_limit_confirm` закрывает разрыв между текстом и опорой в коде: сумму для `set_budget_limit` приносит модель, и, если человек её не называл, она вправе её придумать. Порог `MIN_SENSIBLE_LIMIT` ловит грубую ошибку разбора, но не самодеятельность. Поэтому инструмент лимит не пишет — он готовит смену, наружу уходит детерминированный вопрос (не текст модели, который обычно уже рапортует о свершившейся смене), а запись делает согласие. Диалоговый ввод лимита через `/start` подтверждения не требует: там число печатает сам человек.

Переход в `base` происходит после получения ответа либо по таймауту (состояние старше часа считается протухшим — пользователь ушёл, не ответив). Свободный вопрос в состоянии ожидания сбрасывает `pending`: человек передумал отвечать и спросил другое.

Состояние в Postgres, а не в Redis: одной зависимостью меньше, что в закрытом контуре важнее скорости — обращений к состоянию единицы на сообщение.

## 8. SGR-цикл

```python
class GetExpensesArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    period: str
    category: str | None = None

class SearchHouseholdArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    query: str

# ... своя схема аргументов на каждый инструмент

class NextStep(BaseModel):
    model_config = ConfigDict(extra="forbid")
    goal_progress: str
    plan_remaining_steps: Annotated[list[str], Field(min_length=1, max_length=5)]
    decision_summary: str
    call: GetExpensesCall | SearchHouseholdCall | ... | NoToolCall   # discriminated union по полю tool
    task_completed: bool
```

Отличия от `a07`:

- **Аргументы типизированы.** `tool_args: dict` пропускал правильное имя инструмента с выдуманными аргументами. Discriminated union связывает имя со схемой его аргументов, и несоответствие отсекается валидацией, а на первом уровне — прямо сэмплером.
- `tool` внутри union — `Literal`: выдуманное имя не пройдёт.
- Честный `response_format` вместо поиска JSON регуляркой и слоя дефолтов.
- Поле `remaining_attempts` убрано — счётчик ведёт цикл, модели незачем его выдумывать.
- Порядок полей: `goal_progress` и `plan_remaining_steps` стоят раньше выбора инструмента, поэтому к моменту выбора модель уже написала, чего ей не хватает. **На первом уровне это структурное свойство** — сэмплер выдаёт поля в порядке схемы; на третьем уровне остаётся эвристикой промпта.

**Контролируемый отказ.** После второго неудачного разбора шаг завершается явной ошибкой; частично разобранные данные не используются. Агент сообщает, что шаг выполнить не удалось, и переходит к следующей попытке либо завершает работу с честным ответом — молчаливой подстановки дефолтов, как в `a07`, нет.

**Приведение типов запрещено.** Разбор на третьем уровне допускает только снятие markdown-обёртки и выделение внешнего JSON-объекта. Приводить `"45 000 ₽"` к числу или `"да"` к `true` нельзя: ошибочный ответ стал бы формально валидным, а речь о денежных суммах.

По завершении (`task_completed = true`) делается **отдельный вызов финализации** — в `a07` пользователю уходило внутреннее `reasoning` последнего шага, здесь собирается связный ответ по всей цепочке:

```python
class FinalAnswer(BaseModel):
    model_config = ConfigDict(extra="forbid")
    summary: str                 # краткий практический вывод
    details: list[str]           # цифры и факты
    scenarios: list[str]         # если однозначного ответа нет
    source_keys: list[str]       # ТОЛЬКО идентификаторы: "PF-007", "HH-004", "cbr:USD@2026-08-22"
```

**Источники модель не сочиняет.** Она возвращает только ключи, а инструменты по ходу работы складывают фактически использованные идентификаторы в реестр шага. Код сверяет `source_keys` с реестром, отбрасывает то, чего в нём нет, и собирает человекочитаемые ссылки сам — по `documents.document_key` и по дате ответа MCP. Свободный текст в поле источника позволял бы придумать несуществующую главу.

**`disclaimer` ставит код, а не модель.** Детерминированный policy-флаг: тема попала в инвестиционный список ключей, или в ответе есть данные с датой старше порога, или сработало правило про курс ЦБ против курса банка. Решение «нужна ли оговорка» слишком важно, чтобы оставлять его на усмотрение модели.

**Трансляция шагов** в чат остаётся демонстрацией работы SGR (как в `a08`), но управляется флагом: включена в демо-режиме, выключена в закрытом контуре. Содержанием ответа внутренние поля не становятся никогда — для этого есть `FinalAnswer`, а пользовательское поле шага называется `decision_summary` и chain-of-thought не раскрывает.

## 9. Внешний MCP

`uvx atomno-mcp-cbr-rates@0.1.10`, транспорт stdio, ключей не требует. Версия пинуется, чтобы за день до защиты ничего не поехало.

Инструменты и их роль:

- `get_rate(char_code, on_date?)` — пересчёт долларовых накоплений в рубли
- `inflation(year_from?, year_to?)` — **справочный ориентир** при индексации прошлых трат. Основой расчёта служит правило семьи из `HH-003` (12–15% в год плюс сверка живых цен): общий индекс потребительских цен не отражает динамику авиабилетов и отелей. Цифру из MCP агент называет грубой оценкой явно, а не выдаёт за расчёт
- `key_rate(...)` — ориентир доходности вкладов при сравнении «гасить кредит или копить»
- `statistics()` — сводка одним вызовом
- `history_rates(...)` — динамика курса

Каждый ответ содержит `date` и `source`, что позволяет агенту честно датировать цифры.

Описания инструментов и их `inputSchema` берутся из `tools/list` и вкладываются в системный промпт — сервер строго валидирует аргументы, придуманные имена полей не пройдут молча.

## 9а. Два пути обработки сообщения

Не всякий вопрос стоит гнать через SGR-цикл. Регулярные запросы обслуживаются детерминированно — чистый SQL и шаблон, без единого обращения к модели:

| Команда | Что делает |
|---|---|
| `/start` | приветствие, перевод в `awaiting_limit`, запрос месячного лимита |
| `/status` | «Потрачено X из Y (Z%), остаток на N дней» — по `get_budget_status()` |
| `/balance` | остатки по счетам: общие и личные спрашивающего, все валюты — по `_balance_rows()` |
| `/report` | отчёт по категориям за месяц плюс inline-кнопка «Совет от ИИ» |
| `/help` | список команд и примеры вопросов |

Свободный текст идёт агенту: либо это совершённая операция — трата («потратил 3200 в ВкусВилле» → каскад категоризации) или доход («получил зарплату 250 тысяч» → категория дохода), — либо содержательный вопрос → SGR-цикл. Один классификатор различает все три случая за один вызов модели: разбор на трату и доход отдельными вызовами стоил бы вдвое дороже на каждом сообщении.

**Кнопка «Совет от ИИ»** под отчётом обрабатывает `callback_query` и запускает наставника: берёт текущую картину трат из SQL, ищет релевантный принцип в `PF` и договорённость в `HH`, отдаёт разбор со ссылками на источники.

**Отчёт по расписанию** — cron раз в день присылает сводку вчерашних трат плюс статус с начала месяца (`daily_report`/`send_scheduled_report`). Отдельный недельный отчёт по категориям с отметкой «уложились/не уложились в лимит» **не реализован** (финальная волна правок, пункт 10) — при желании его несложно добавить тем же способом (ещё одна детерминированная функция плюс второй `cron`-вызов с `--report-cron --weekly` или отдельным флагом), но в текущей поставке есть только ежедневный путь.

Разделение даёт не только соответствие ожиданиям задания, но и страховку: если локальная модель окажется медленной, `/status`, `/balance` и `/report` отвечают мгновенно, и бот не выглядит зависшим. Тяжёлый путь — только там, где шаблоном не обойтись.

**Личная доля дохода.** Правило `personal_money_share_pct` объявляет, какая часть дохода считается личными деньгами супруга. Сид проводит эту долю отдельной проводкой на личную карту: без неё личные счета живут без единого поступления и уходят в минус тем глубже, чем длиннее история, — правило есть в данных, а самих денег нет. Найдено при добавлении `/balance`: команда показывала бы этот минус каждый день.

## 10. Приватность

```
личный чат:  видно common + собственный scope
общий чат:   видно только common
```

Во втором правиле смысл: в общем чате не показывается даже собственное личное — рядом второй супруг.

Соответствие `telegram_id → person` задаётся в `.env`. В CLI то же самое эмулируется флагами `--as husband|wife --chat private|group`, поэтому приватность демонстрируется одним человеком.

Реализация — функция `visible_scopes(person, chat_type)`, результат которой попадает в `WHERE` каждого запроса и в фильтр RAG. Данные, которые нельзя показывать, в контекст модели не попадают вообще.

## 11. Закрытый контур, конфигурация и поставка

### Периметр

Точная формулировка: это **локальное ядро с контролируемыми внешними каналами**, а не полностью закрытый контур. Ядро — база, эмбеддинги, корпуса, вся логика — локально всегда. Что уходит наружу, зависит от режима, и режимов ровно два:

| | Демо и сдача | Закрытый контур |
|---|---|---|
| Модель | `gpt-oss:120b-cloud` | локальная из лестницы |
| Канал | Telegram | CLI |
| Данные | синтетические (сид-база) | реальные |
| Уходит наружу | тексты сообщений в Telegram, запросы к облачной модели, коды валют и годы в MCP | коды валют и годы в MCP |
| MCP | `uvx` тянет пакет с PyPI при первом запуске | пакет установлен заранее |

В демо-режиме утекать нечему по построению: сид-база синтетическая, реальных финансов семьи в ней нет. В закрытом контуре наружу идёт единственный вызов — курс и инфляция у Банка России; в запросе только код валюты и год, без сумм, категорий и имён.

Прежняя формулировка «данные периметр не покидают никогда» была неверна: Telegram — внешний облачный канал, а демо-модель работает в облаке Ollama.

### Две среды

| | Модель | Уровень схемы |
|---|---|---|
| Разработка и демо (VPS, 8 ГБ) | `gpt-oss:120b-cloud` | третий — схема не принуждается |
| Поставка (закрытый контур) | по железу заказчика, см. лестницу ниже | первый — constrained decoding |

Для демо размер модели не имеет значения: веса лежат в облаке Ollama, бесплатный уровень покрывает `gpt-oss:120b` и `nemotron-3-super`. Берём самую сильную из бесплатных — выбор инструмента на демо-сценариях будет точнее.

Измерено: локальная Ollama принуждает схему (проверено на `tinyllama` — вернула поля строго по схеме); облачная её отбрасывает (проверено на `gpt-oss:120b`, `gpt-oss:20b`, `gemma4:31b`). Что локальный `gpt-oss:20b` попадёт в первый уровень — вывод из механики (принуждение работает на уровне сэмплера, от модели не зависит), подтверждается на месте командой `--check-backend`.

### Лестница моделей закрытого контура

`OLLAMA_MODEL` — параметр конфигурации, интерфейс к модели единый. Но безразличной к выбору архитектура не является: от модели зависят формат ответа, качество выбора инструмента, задержка и частота повторов. Поэтому каждая ступень проходит одинаковый набор smoke-сценариев с замером p95 задержки; «20B запускается на CPU» само по себе не означает пригодности для Telegram-бота.

Модель подбирается под железо заказчика:

| Модель | Вес | Требуется на месте |
|---|---|---|
| `gpt-oss:20b` | ~13 ГБ MXFP4 | станция 16 ГБ, идёт даже на CPU |
| `gemma4:31b` | ~20 ГБ Q4 | станция 32 ГБ |
| `gpt-oss:120b` | ~60 ГБ MXFP4 | H100 80 ГБ, Mac Studio 128 ГБ или сервер 96+ ГБ |
| `nemotron-3-super` | ~60 ГБ NVFP4 | то же по памяти; MoE — активных параметров меньше, инференс быстрее плотной модели того же размера, NVFP4 раскрывается на Blackwell |

Требование «работает на небольших ресурсах» выполняется нижней ступенькой и от этого только выигрывает: система, идущая на станции с 16 ГБ и масштабирующаяся до GPU-сервера, сильнее системы, которая требует GPU-сервер как минимум.

Остальные компоненты одинаковы на любой ступени: эмбеддинги `qwen3-embedding:0.6b` — 0,6 ГБ диска и ~0,7 ГБ памяти, Postgres с pgvector — около 0,3 ГБ, процесс агента — 0,2 ГБ.

**Различие, которое обязан знать код:** `gpt-oss` и `nemotron` возвращают рассуждения отдельным полем и могут отдать пустой `content`; `gemma4` отдельного поля не имеет и пустого `content` не даёт, но оборачивает JSON в markdown. Слой LLM обрабатывает оба поведения.

### Конфигурация

Переменные из учебных примеров сохранены без изменений; добавлены только новые. Полный список с умолчаниями и подстановками — [docs/configuration.md](configuration.md), он же единственное место, где эти значения описаны.

**Состав поставки:** таблица файлов — в [PROJECT_OVERVIEW.md](../PROJECT_OVERVIEW.md).

Порядок первого запуска: поднять Postgres → `pip install -r` → `--init` (схема + загрузка обоих файлов данных + индексация корпуса) → `--check-backend` → CLI-проверка → Telegram.

## 12. Демо-сценарии

Прогоняются до сдачи; покрывают каждую ветку системы.

| # | Вопрос | Что задействовано |
|---|---|---|
| 1 | «Сколько потратили на продукты в июле?» | Инструмент |
| 2 | «Потратил 3200 в ВкусВилле» | Ввод + категоризация по алиасу |
| 3 | «Потратил 4100 в Ашане» | Ввод + LLM-категоризация + дозапись алиаса |
| 4 | «Сначала гасить кредит или копить подушку?» | RAG (knowledge) + источники |
| 5 | «Хватит ли нам до зарплаты?» | Прогноз кассового разрыва |
| 6 | «Сколько у нас всего накоплений в рублях?» | Инструмент + MCP (курс USD) |
| 7 | «Отпуск обойдётся в 280 тысяч — можно ли закрыть часть суммы из долларовых накоплений по текущему курсу?» (переформулировано, раунд ревью 3 задачи 12 — исходный текст в рублях не давал MCP-курсу ЦБ повода включиться) | RAG (household) + инструмент + MCP |
| 8 | «Сколько закладывать на отпуск в этом году?» | `search_household` (`HH-003`, `HH-004`) + MCP (инфляция как ориентир) |
| 9 | «Насколько нам хватит подушки?» | Инструмент + RAG (норма резерва) |
| 10 | Один вопрос про личные траты в личном и в общем чате | Приватность |
| 11 | `/start` → ввод лимита → `/status` | Состояния диалога, быстрый путь |
| 12 | `/report` → кнопка «Совет от ИИ» | `callback_query` + наставник на RAG |

Сценарий 7 — главный для защиты: три источника (корпус, база семьи, ЦБ) в одном ответе, каждый в своей роли.

## 13. Риски

**Пустой ответ DeepSeek при JSON Output** — задокументированное поведение. Снимается повтором с валидацией; если повтор тоже пуст, шаг помечается ошибкой и агент переходит к следующей попытке.

**Слабый бэкенд.** `--check-backend` показывает режим заранее. Если строгий режим недоступен, работает `json_object` с повтором.

**Недоступность MCP.** Сеть или PyPI могут подвести. Агент должен переживать отказ инструмента: сообщать, что курс получить не удалось, и отвечать по имеющимся данным, а не падать.

**Зацикливание SGR.** Лимит шагов и передача уже сделанных вызовов в промпт (как в `a07`).

**Токен Telegram.** Отдельный бот от @BotFather; переиспользовать токен другого бота нельзя — 409 и отвал обоих.

## 14. Осознанно за рамками прототипа

Программа ежедневных уроков с прогрессией тем и историей прочитанного; отдельная коллекция актуальных норм с датами; импорт банковских выписок; разграничение доступа тоньше трёх областей видимости; веб-интерфейс. Всё это — продукт, не учебный прототип.
