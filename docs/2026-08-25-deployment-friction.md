# Разворачивание: оценка сложности и пути упрощения

Дата: 2026-08-25.
Контекст: практический опыт локального развёртывания агента (исправления
поставки — merged в PR #2). Здесь — честный разбор, где
разворачивание спотыкается и что стоит упростить в первую очередь.

---

## Коротко

- Код является цельным и разворачивается: `--doctor` честно диагностирует,
  `--init` грузит корпуса и сид, CLI/Telegram отвечают на вопросы, MCP ЦБ
  отдаёт курсы, архитектура SGR + RAG + инструменты + строгие схемы — на месте.
- **Трение сосредоточено не в коде, а в подготовке окружения**, и особенно в
  **модельном слое** (Ollama + подбор модели под железо).
- Конкретные падения «из коробки» (inline-комментарии `.env`, отсутствие
  `socksio`, подготовка тестовой БД) уже закрыты в **PR #2**; ниже — оставшееся
  трение и план упрощения.

---

## Сложность по шагам

| Шаг | Сложность | Что спотыкается |
|---|---|---|
| Python 3.11+ | легко | — |
| Docker + Postgres(pgvector) | легко | **порт 5433 часто занят**; схема создаётся только на пустой базе |
| Виртуальное окружение | легко | на Debian/Ubuntu без `python3-venv` venv создаётся **без `pip`** → `.venv/bin/pip install` падает |
| Ollama + модели | **тяжело** | главный барьер (см. ниже) |
| `.env` | после PR #2 — ок | было падение на inline-комментариях пустых ключей |
| MCP Банка России (uvx) | средне | внешний сетевой сервис: `uvx` из PyPI + доступ к cbr.ru; в закрытом контуре недоступен |
| Telegram | зависит от региона/провайдера | в РФ прямой Telegram может глушиться (DPI) — тогда нужен SOCKS-прокси `TELEGRAM_HTTP_PROXY` |
| Скорость ответа | тонко | неверная модель → 240+ с на один вопрос (наблюдалось на `smtek/Qwen3.8-27B:Q3_K_M`) |

## Главный барьер: модельный слой

Лестница моделей (`gpt-oss:20b`, `gemma4:31b`, `gpt-oss:120b`,
`nemotron-3-super`) требует либо мощного железа (16–60+ ГБ), либо облачного
запуска. Практические варианты для внешнего пользователя:

- **Локальная модель** — нужен GPU/большая память, и инференс на CPU-машинах
  медленный (27B-модель на ноутбуке отвечала >240 с — бот в такой конфигурации
  непригоден для интерактива).
- **Облачная (`gpt-oss:120b-cloud`)** — реалистичный путь для обычного ноутбука,
  но это маршрут «локальная Ollama → ollama.com»: нужен интернет, аккаунт/квоты
  и корректная настройка `OLLAMA_URL`. Этот путь наименее документирован.

Вывод: в наблюдавшемся контуре **модельный слой — главный порог входа**, и
упрощение тут упирается в железо/облако, а не в код. Это наблюдение одного
практического развёртывания, а не универсальный вывод для любых конфигураций.

## Пути упрощения (по приоритету)

### 1. Расширить `setup.sh` — наибольший выигрыш, минимум кода

Новый параллельный entry point не нужен: `setup.sh` уже создаёт venv, ставит
зависимости, готовит `.env` и запускает `--doctor`. Разумнее **встроить в него**
оставшееся механическое (идемпотентно, по обнаруженному состоянию):

- есть Docker → поднять Postgres из compose (с фолбэком на свободный порт, если
  5433 занят);
- корректно создать venv (подсказка про `python3-venv`/`uv` — venv без `pip` уже встречался);
- установка зависимостей;
- проверить/подготовить Ollama и нужные модели (`ollama pull`);
- сгенерировать/дозаполнить `.env` с автоматическим `PG_DSN` из поднятого compose;
- прогнать `--doctor`, при необходимости `--init`.

Итог: вместо ~8 ручных шагов — «подготовь окружение и запусти один скрипт»,
без нового параллельного скрипта. `setup.sh` остаётся единственной точкой входа.
Идемпотентно: повторный запуск ничего не ломает.

### 2. Смонтировать агент целиком в `docker-compose` — `docker compose up -d` = всё

Сейчас в compose только Postgres, сам агент крутится в системном Python.
Добавить сервис `ollama` (runtime-образ + volume моделей + шаг pull/init) и
`agent` (образ с зависимостями) —
пользователь не трогает Python-окружение и venv на хосте вообще. Самое сильное
структурное упрощение, но работы больше: прогрев модели, проброс `OLLAMA_URL`,
том для данных. Оправдано, если цель — максимальный «zero-config» деплой.

### 3. Сократить `.env` до минимума + авто-генерация

Скрыть `ROUTER_*`, `LLM_STRUCTURED_MODE`, `BROADCAST_STEPS` за разумными
дефолтами; `OLLAMA_URL`/`EMBED_URL` по умолчанию совпадают; `PG_DSN`
подставляется автоматически. Остаются 3–4 ключа, которые реально осознанно
заполняет человек: модель, строка БД, токен Telegram (опционально), id-шники.
Снижает порог и число ошибок.

### 4. Облачная модель по умолчанию (turnkey) + предупреждение о задержке

Самая частая беда — неудачный выбор модели под медленное железо. Добавить в
`--doctor`/`--check-backend` **замер задержки ответа** с предупреждением при
высокой (например, «модель слишком медленная для режима чата, рассмотрите
облачную»). Важно: текущий вызов LLM — **non-streaming**, поэтому замеряется
полная латентность ответа, а не TTFT; для настоящего «времени до первого токена»
проверку пришлось бы перевести на streaming. Но даже полная латентность сразу
вскрывает «модель не подходит под это железо», а не заставляет биться вслепую
после восьми минут индексации.

### 5. Внешний MCP — целевое состояние «опциональный» (сейчас не полностью)

Рантайм мягко деградирует: при недоступности сервера ловится исключение и
отвечается «инструменты сейчас недоступны». **Но** на текущий момент MCP Банка
России — не полностью опциональный: README требует `uvx`, а `--doctor` считает его
отсутствие `ПРОБЛЕМОЙ` и возвращает ненулевой код. Поэтому пункт стоит
рассматривать как **предлагаемое целевое состояние**: для настоящей опциональности
нужно отдельно сменить doctor/config contract — сделать `uvx` необязательным, а его
отсутствие — `ВНИМАНИЕ`, а не `ПРОБЛЕМА`.

## Кому и насколько легко

| Профиль | Оценка |
|---|---|
| Разработчик с Docker + Ollama + Python | легко (пара команд) |
| Пользователь с GPU-машиной | средне (нужно подобрать модель из лестницы) |
| Обычный ноутбук без GPU | средне-трудно (нужна облачная модель + сеть) |
| Закрытый контур без внешней сети | сложно (нет MCP ЦБ, нет облака — локальная модель и большой RAM) |

## Рекомендация

1. Сначала — расширение `setup.sh` (пункт 1): дёшево, снимает 80% ручного труда.
2. Затем, если цель — максимальный zero-config — compose с агентом (пункт 2).
3. Параллельно — сокращение `.env` (пункт 3) и предупреждение о задержке
   (пункт 4): они убирают самые частые ошибки новичка.

Части, которые не стоит трогать при упрощении: **учебная читаемость кода** и
строгие схемы SGR — это и есть образовательная и проверяемая суть проекта.
Автоматизация (расширение `setup.sh`, compose) должна быть **сверху**, не подменяя
основной код и не мешая прохождению демо-сценариев `run_demo.py`.

## Приложение (2026-08-26): обрыв Telegram-поллинга под DPI

Наблюдение из практической эксплуатации бота в регионе, где выход в
Telegram возможен только через SOCKS-прокси (`TELEGRAM_HTTP_PROXY`):

**Симптом.** Бот «перестаёт отвечать»: кажется, что он умер, хотя
`--doctor` и LLM-слой живы, а единичные `getMe`/`sendMessage` через тот же
прокси проходят.

**Диагноз.** В журнале бота — повторяющиеся
`telegram.error.NetworkError: httpx.ConnectError` в `socks_proxy.py:start_tls`
только на `get_updates` (длинный опрос). Инспекция трафика распознаёт и рвёт
долгоживущее TLS-соединение к `api.telegram.org`; короткие одиночные запросы
проходят. Отдельное замечание: при ручной проверке через `curl getUpdates`
легко получить `409 Conflict: terminated by other getUpdates request` — это
нормально (тестовый запрос перебивает активный опрос), а не признак второго
экземпляра бота.

**Мера смягчения (этот PR).** `read_timeout` 40 → 20 с и `connect_timeout`
20 → 10 с в `updates_request` (`run_telegram`). Важно, чем эта правка НЕ
является: она не укорачивает жизнь соединения. Длительность одного
`getUpdates` задаёт параметр `timeout` у `run_polling` (10 с по умолчанию),
`read_timeout` — лишь сколько клиент ждёт ответа, а соединение httpx
переиспользует между запросами, и опрос идёт встык — оно живёт всё время
работы бота. Что правка даёт: убитое соединение обнаруживается за 20 с
вместо 40 — окно глухоты на инцидент вдвое короче, — а неудачные попытки
переподключения отваливаются за 10 с вместо 20, и restart-цикл
`run_polling` (`network_retry_loop`) быстрее добирается до свежего
соединения. `read_timeout` обязан оставаться больше длинного опроса (10 с).
Это **смягчение**, а не решение: сам внешний фактор в коде не устраним.
Если сбой всё же происходит — достаточно перезапуска бота.

**Что не является решением.** Отключение `TELEGRAM_HTTP_PROXY` или прямое
подключение лишь переносит проблему; устойчивый вариант — держать опрос за
прокси, через который долгоживущие соединения к Telegram фактически
проходят: это свойство конкретного канала, и проверяется оно только опытом.
